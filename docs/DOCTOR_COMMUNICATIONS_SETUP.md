# Doctor communication and account setup

The doctor workspace now includes an Inbox preview, Inbox and Sent folders, and a composer for other doctors, hospital administrators and the doctor's assigned patients. Admins can send leave notices, patient messages and announcements to one doctor or all active doctors. Leave request/status changes create internal inbox notifications. Only a message's recipient can mark it read. Staff messages are private to their sender and recipient; patient communication remains limited to the assigned doctor.

New doctor registration requires an email. A unique username and a cryptographically random temporary password are generated on the server. Password generation does not send credentials to the language model. Temporary passwords expire after 24 hours and require a first-login password change. Passwords are stored as salted hashes; plaintext credentials are sent only in the addressed login email and are not kept in the database, audit trail or browser response. Doctors change passwords from the login page using their current password. Password changes revoke old sessions, enforce CSRF protection and limit failed attempts.

The configured sender is **pamindu39@gmail.com**. Email needs Gmail authorization. Configure server-only `GMAIL_OAUTH_JSON` (JSON containing client_id, client_secret and a refresh_token authorized for Gmail sending), or `GMAIL_APP_PASSWORD`. Local file variants append `_FILE` to the variable name. Gmail app passwords require Google's two-step verification; do not use the ordinary Gmail password. Prefer OAuth when available. On Vercel, store secrets as sensitive environment variables, never in this repository. `ADMIN_EMAIL` may explicitly set the sender, and `CATATRIAGE_PUBLIC_URL` sets the login URL in the email.

The admin care-team card shows provider acceptance or a configuration/failure message. It never equates acceptance with inbox delivery. After configuring the sender, **Send new login email** issues fresh temporary credentials. A failed resend preserves the existing password. Existing doctors are not automatically reset by deployment.

Final surgery confirmation saves a notification snapshot and opens a confirmation pop-up on the calendar. It includes the exact **Surgery Appointment Confirmation** wording requested, the patient's name, date and time. The doctor's sent box retains the message and send status. Duplicate submissions for the same current booking do not send a second notification. Changing the booking creates a new notice.

Automatic WhatsApp requires `WHATSAPP_ENABLE=true`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, a supported `WHATSAPP_GRAPH_VERSION`, `WHATSAPP_SENDER_PHONE`, and an approved `WHATSAPP_SURGERY_TEMPLATE` with `WHATSAPP_TEMPLATE_LANGUAGE` (default `en`). The template's body has four ordered text parameters: patient name in the greeting, patient name in the details, date, and time. Register the exact requested static text in WhatsApp Business before enabling it.

Multiple verified doctor senders can use server-only `WHATSAPP_DOCTOR_CONFIG_JSON` (or its `_FILE` variant), keyed by the sender's international digits. Each entry contains sender_phone, phone_number_id, access_token, template_name, graph_version and language. A doctor's profile number must match that verified sender. The application cannot send from an arbitrary personal WhatsApp number.

Without these credentials/template, the booking succeeds and the message is marked **stored not sent**. The pop-up offers **Open WhatsApp message**, which prepares the same text for the doctor to send manually using their logged-in WhatsApp account. No automatic WhatsApp service, billing or paid plan was activated in this update. Check provider pricing/allowances before enabling automated template sends. Provider acceptance is displayed as accepted, not delivered; delivery webhooks are outside this change.

Database addition: `deployment/cloud/doctor_communications.sql` creates private hospital-schema tables for staff messages, outbound notices, account security and authentication attempts, and adds the doctor email field. RLS is enabled; public, anon and authenticated roles have no access. The app's restricted database role accesses them through authenticated server routes. Existing patient records, image rounds, priorities, bookings and passwords are preserved.

Official references: [Gmail SMTP/OAuth](https://developers.google.com/workspace/gmail/imap/imap-smtp), [Gmail app passwords](https://support.google.com/accounts/answer/185833), [WhatsApp template management](https://whatsappbusiness.com/blog/manage-message-templates-whatsapp-business-api/).
